# ADR 006 — B5.1: Should the CLI adopt a framework?

**Status:** decided — a declarative command table, no framework. **Confidence:** medium-high.
**Date:** 2026-09-08. Registry figures from the sweep in `audit/DEPENDENCIES.md`.

## The problem

`ho` is 22 files and 1 273 lines with 18 top-level commands. Two things are structurally wrong (B5.1):

1. `apps/cli/src/commands/help.ts` is a **46-line hand-maintained `USAGE` string** with nothing tying it to
   the modules that implement the commands. Each command re-declares its flag list inside `parse(...)`, so a
   new flag is invisible in `--help` until someone remembers to edit the string.
2. `apps/cli/src/commands/run.ts` is an **84-line switch with 18 near-identical arms**, each awaiting one
   function and returning.

Both are drift machines. The text is accurate today, which is luck rather than structure.

## Options

### 1. Keep it as is — reject

**Gain:** nothing to do. **Lose:** the drift stays. The brief explicitly asks for CLI improvement and this
is the CLI's clearest structural weakness.

### 2. `commander@15.0.0` — reject

**State:** published 2026-09-02, **451 M weekly** (the most-downloaded option by far), MIT, **0
dependencies**. Passes every maintenance criterion comfortably.
**Gain:** generated `--help` from the command definitions, so the drift disappears; subcommands, typed
options, `--version`, unknown-option errors, all battle-tested.
**Lose:** its option model is imperative and string-keyed (`.option("-p, --path <dir>")`), so values come
back as a loosely typed object that this codebase would immediately re-validate with Zod anyway — the
`str()`/`required()` helpers in `apps/cli/src/args.ts` exist precisely to type that boundary. Commander
would remove `parse()` (25 lines) and `USAGE` (46 lines) while adding a dependency and a _second_
validation style beside the Zod one.
**Migration:** all 22 CLI files touched mechanically, `run.ts` deleted. **Code deleted:** ~130 lines.

### 3. `citty@0.2.2` — reject

**State:** published 2026-08-20, 27.5 M weekly, MIT, 0 dependencies, unjs, TypeScript-first with typed
`args` and generated help. The most modern fit for a Bun/TS project.
**Lose:** it is **pre-1.0**. B25 permits experimental dependencies, but the reversal cost is not trivial
here: the CLI's argument surface is its public interface, and a breaking 0.x change would mean re-shaping 22
files. The win over option 4 is small against that.
**Verdict:** reject on risk-to-benefit, not on maintenance.

### 4. A declarative command table of our own — **recommended**

Replace `run.ts`'s switch and `help.ts`'s string with one table that is the single source of both:

```
type Command = {
  name: string;
  summary: string;
  usage: readonly string[];   // the lines --help prints for this command
  flags: readonly string[];   // what parse() accepts
  booleans?: readonly string[];
  run: (args: readonly string[]) => Promise<void>;
};
```

`run()` becomes a `Map` lookup plus one `await`; `--help` is generated by walking the same table; each
command module exports its own entry, so a flag declared once appears in the help text automatically.
`parse()` in `args.ts` stays — 25 typed lines over `node:util`'s `parseArgs`, a first-party API with
`multiple: true` support (proved empirically this session, B15.3), and the reason the CLI has no
argument-parsing dependency at all.

**Gain:** the drift is eliminated structurally, the 84-line switch becomes ~15 lines, `help.ts` becomes a
generator rather than a literal, and no dependency is added. Combined with B5.2 (a human summary plus a
global `--json`) and B5.4 (`@clack/prompts` for the hidden password prompt), the CLI gets what a framework
would have given it.
**Lose:** we own ~40 lines of table-walking and help formatting that commander would own instead. That is
the honest cost, and it is why confidence is medium-high rather than high — a reasonable person would pick
commander here.
**Migration:** 18 command modules gain a small exported descriptor; `run.ts` and `help.ts` are rewritten.
Mechanical, reversible, each module independently reviewable.
**Code deleted:** ~110 lines net of the ~40 added.
**Perf/RAM:** marginally better — no framework to construct at startup, which counts a little for a CLI
compiled with `bun build --compile` and started per invocation.

### Rejected on maintenance grounds

## Recommendation

**Option 4.** The reason to prefer it over commander is specific rather than ideological: the CLI's
arguments are already typed through `parse()` plus Zod schemas from `@ho/protocol` (`TaskId.parse`,
`AgentRole.parse`, `SecretKeyName.parse`), and commander's string-keyed option model would sit _beside_
that rather than replace it. The problem is not "we lack an argument parser" — Bun ships one — it is "the
help text is not derived from the commands". A table fixes exactly that, for ~40 lines we own.

**If this call is wrong** it is cheap to reverse: the table's shape (`name`, `flags`, `run`) maps almost
directly onto commander's `.command().option().action()`, so switching later is a mechanical rewrite of one
file plus 18 descriptors.
